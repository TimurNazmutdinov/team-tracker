# ADR-006. Демо-режим: автор действий, порядок в списках, версия seed

- **Статус:** принято
- **Дата:** 2026-10-28

## Контекст

На этапе 4 появляются изменения данных: создание и правка задач, комментарии, перенос по спискам. Входа в систему пока нет ([capabilities.md](../capabilities.md), раздел 2), но в истории и у комментариев должен быть автор. Порядок задач (`order`) должен меняться перетаскиванием без конфликтов между списками. Демо-данные обновляются вместе с кодом, а у пользователей в браузере лежат старые копии.

## Решение

1. **Автор действий.** В демо-режиме действия выполняются от имени участника, выбранного в меню профиля («Работаю как»). Выбор хранится в браузере; по умолчанию — первый участник.
2. **Порядок в списках.** Значения `order` не пересчитываются по всему проекту: при переносе или перестановке только участники затронутого списка (спринта или бэклога) обмениваются имеющимися значениями `order`. Значения остаются уникальными, чужие списки не затрагиваются.
3. **Подзадачи не имеют своего места в списках.** Они показываются внутри родителя и переносятся вместе с ним (ADR-003, п. 9).
4. **Версия seed.** В `data/seed.json` есть поле `version`. Если сохранённые в браузере данные относятся к другой версии, они сбрасываются, а пользователь получает уведомление. При любом изменении seed версию нужно увеличить (это делает человек; формат поля проверяет `scripts/check_seed.py`).
5. **Границы слоёв.** Правила и запись истории — чистые функции в `src/domain/actions.ts`, получающие данные и источники времени и id как аргументы и возвращающие набор изменений. Экран вызывает их через `useActions`, который читает данные, применяет логику и отправляет изменения в хранилище одной операцией.

## Рассмотренные варианты

- **Переписывать `order` у всех задач проекта при каждом переносе** — больше записей и больше шансов на конфликт при будущей работе нескольких людей.
- **Дробный `order`** — схема данных требует целое число.
- **Мигрировать устаревшие данные вместо сброса** — для демо-данных не оправдано.

## Последствия

- С появлением входа (ADR-007, предстоит) пункт 1 заменяется реальным пользователем сессии.
- История остаётся воспроизводимой: тесты проверяют, что она приводит к текущим статусу и спринту каждой задачи.
- Запись о смене `order` в историю не пишется: это не событие жизни задачи.
