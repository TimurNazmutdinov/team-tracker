# ADR-015. Надёжность: сквозные тесты, доступность, скорость, журнал ошибок

- **Статус:** принято (часть 2 доработок)
- **Дата:** 2026-10-29

## Контекст

Продукт вырос до нескольких экранов и ролей, а проверялся юнит-тестами логики и ручными прогонами. Нужно ловить поломки главного пути пользователя и доступности автоматически, убедиться, что на тысячах задач экраны открываются быстро, и дать администратору способ разобраться с ошибкой без доступа к чужому компьютеру.

## Решение

**1. Сквозные тесты (Playwright) — только в CI.** Они лежат в отдельном пакете `e2e/` со своими зависимостями (`@playwright/test`, `@axe-core/playwright`), поэтому обычные `npm ci`, `npm test` и запуск на компьютере пользователя браузеров не требуют. Тесты идут против настоящего сервера: `npm run db:seed && npm run start` на чистой базе PGlite во временной папке (порт 3100, регистрация открыта, первая учётка — администратор). Главный путь: вход → создание задачи → планирование (перенос в спринт пакетом) → доска (смена статуса) → закрытие спринта с переносом → «Прошлые спринты» → отчёт → резервная копия → «О программе» и скачивание диагностики. Задание CI — `e2e` (параллельно `check`); публикация демо ждёт оба. Локально: `cd e2e && npm ci && npx playwright install chromium && npx playwright test`.

**2. Доступность.** После сквозного теста axe (WCAG 2.0/2.1 A и AA) проверяет экран входа и девять ключевых экранов в светлой и тёмной версиях гаммы; любое нарушение роняет тест. Первый прогон нашёл одно: `aria-label` на `<span>` без роли у значков points — добавлена `role="img"`.

**3. Нагрузочные данные и бюджеты скорости.** `src/domain/loadgen.ts` генерирует детерминированный набор: 10 проектов, 50 спринтов (по три закрытых, идущий и запланированный на проект), 10 000 задач (эпики, Story/Task/Bug, подзадачи), ≈ 38 000 записей истории, связи и комментарии; набор проходит `parseDataset` и воспроизводится по истории. `npm run load:data [файл]` пишет его в JSON для `SEED_FILE=… npm run db:seed`. Тесты `src/domain/load.test.ts` и `server/src/load.test.ts` держат бюджет **< 1 с** на доску всех проектов, планирование и ёмкость, «Прошлые спринты», отчёты и на чтение и запись на сервере. Найдено и исправлено:

| Узкое место | Было | Стало |
|---|---|---|
| Расчёт по истории (`totals.ts`): для каждой задачи фильтровалась вся история, O(задачи × история) — velocity и ёмкость по всем проектам | ≈ 95 с | ≈ 0,13 с |
| Burndown и итоги спринта проекта (1000 задач) | ≈ 450 мс | ≈ 7 мс |
| Запись изменения (`commit`): загружалась, клонировалась и проверялась вся база | ≈ 1,2 с | ≈ 0,04 с (проверяются только затронутые проекты) |
| Загрузка данных и восстановление копии: все строки одним `INSERT` | падение (предел стека и параметров PostgreSQL) | порциями по 500 |

Чтение данных проекта (задачи, история) — 50–100 мс.

**4. Экран «О программе»** (`/about`, пункт меню профиля; [wireframes.md](../wireframes.md), раздел 18). Версию и сборку видят все; копии, диагностику и журнал — только администратор (новое право `system.diagnose`). Версии клиента и сервера сравниваются: при расхождении показывается просьба обновить страницу. «Собрать диагностику» отдаёт zip: версия, настройки без секретов (строка подключения и пароли не включаются; проверяет тест), состояние копий, журнал ошибок; данных задач и людей в архиве нет. В демо-режиме архив собирается в браузере.

**5. Журнал ошибок.** Сервер пишет в `DATA_DIR/logs/server.log` (500-е ответы, необработанные исключения, неудачные копии), клиент — в `client.log` через `POST /api/client-errors` (без входа, но ≤ 2 КБ сообщение и ≤ 60 записей в минуту) и в последние 50 записей `localStorage` для демо. Формат — JSON-строки. Ротация: файл до 1 МБ, хранится до 5 файлов на журнал; сбой записи журнала не прерывает работу. Одинаковая ошибка клиента чаще раза в 10 секунд не повторяется.

## Рассмотренные варианты

- **Браузерные зависимости в корневом `package.json`.** Тяжёлые для всех; отвергнуто, пакет `e2e/` отдельный.
- **Ограничить скорость только замером в e2e на CI.** Медленные и нестабильные замеры; бюджеты держатся быстрыми тестами логики и сервера, e2e проверяет поведение.
- **Тонкая настройка PostgreSQL (индексы) вместо ограничения проверки проектом.** Основная потеря была в клонировании и разборе всей базы, а не в запросах.

## Последствия

- Каждое новое действие записи проверяется в границах проекта: ссылки на задачи другого проекта (например, родитель или связь) отклоняются как «нет задачи».
- При добавлении экранов их стоит включать в список axe и, если они часть главного пути, в сквозной тест.
- Журналы не входят в резервные копии (это не данные трекера).
