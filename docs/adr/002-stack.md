# ADR-002. Выбор технологического стека (вариант A)

- **Статус:** принято
- **Дата:** 2026-10-28

## Контекст

В [architecture.md](../architecture.md) были предложены два варианта стека. Нужен стек, который подходит опытным разработчикам, даёт быстрый отклик интерфейса, позволяет начать без сервера (данные из `seed.json` и браузера) и без переписывания перейти на API и PostgreSQL ([ADR-001](001-storage-module.md)).

## Решение

Выбран **вариант A**. Версии — всегда актуальная стабильная.

**Фронтенд (сейчас):**

- React + TypeScript, сборка — Vite.
- React Router — маршруты: у каждой задачи, доски и спринта свой адрес.
- TanStack Query — загрузка и кэш данных, работа с модулем хранения.
- Zustand — локальное состояние интерфейса (фильтры, выбранная группировка, тема).
- dnd-kit — перетаскивание карточек на доске и порядок в бэклоге.

**Качество и поставка:**

- Vitest — модульные тесты; ESLint + Prettier — стиль и ошибки; TypeScript в строгом режиме.
- GitHub Actions — lint, typecheck, тесты, сборка; публикация демо на GitHub Pages.

**Бэкенд (позже):**

- Node.js + Fastify, Zod для проверки данных на входе, Drizzle ORM, PostgreSQL.

## Рассмотренные варианты

- **Вариант B — Svelte + Hono + PostgreSQL.** Плюсы: малый бандл, меньше шаблонного кода. Отклонён: меньше готовых библиотек для досок и drag-and-drop, меньше разработчиков с опытом, платформа моложе. Для продукта, который будет жить долго и расти командой, предсказуемость экосистемы важнее выигрыша в размере бандла.

## Последствия

- Один язык (TypeScript) на фронтенде и бэкенде; типы и схемы Zod можно разделить между ними.
- Доменная логика пишется на чистом TypeScript без React — её можно тестировать без UI и переиспользовать на сервере.
- Решения «собери сам» (структура папок, формы, стили) фиксируются отдельными ADR по мере необходимости.
- Если возникнет серьёзная проблема с производительностью больших списков, это решается виртуализацией списков, а не сменой стека.
